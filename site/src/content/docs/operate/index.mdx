The operator CLI is designed as an evidence ladder. Each step isolates one boundary before the next one is introduced, so a failure has a useful category instead of becoming a generic startup error.

## Establish the read-only baseline

<Steps>

1. Create an owner-managed Discord application and bot, then run `npx guildctl` and choose the MCP host first.

2. Review the exact `server-observer` grant, install it into one locked guild, and type that guild ID exactly.

3. Let the command verify the token's application, exact installation, strict non-secret policy, and real child-process stdio path.

4. Open the private selected-host guide, supply the host's protected credential, reload it, and complete the first channel inventory.

5. Use `catalog`, `config validate`, `doctor`, `smoke`, or the manual setup route only when you want independent evidence or need to isolate a failure.

</Steps>

The [first verified read guide](../start/getting-started/) provides the shortest supported route. Use [advanced manual setup and verification](../start/manual-setup/) for release-pinned commands, independent evidence, alternate credential custody, and the complete recovery order.

Once the baseline works, add one outcome at a time:

<Aside type="tip" title="Recipes add bounded authority">

A recipe plans and applies one reviewed policy expansion. It does not bypass Discord permissions, widen exact scope implicitly, or make an immediate write path available.

</Aside>

## Recover and verify

- Use [troubleshooting](./troubleshooting/) for setup, host initialization, policy, credential, Discord, and stdio failures
- Use [release verification](./release-verification/) to distinguish provenance, inventories, signatures, and reproducibility from security claims they cannot make
- Use the [exact contract explorer](../generated/contract-explorer.html) to inspect the callable release without a credential or Discord request
